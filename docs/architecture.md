# 系统架构

## 分层与职责

### 数据层
数据层负责把文档变成可检索的片段：切分、向量化、入库，对应 `app/chunking.py`、`app/embeddings.py`、`app/store.py`。
向量存在 SQLite 的 BLOB 字段里，检索时一次矩阵乘法算出余弦相似度。

### 检索层
检索层提供三个检索器：向量检索、BM25 关键词检索，以及把两者名次融合的混合检索。
它们共用同一个接口 `search(question, top_k) -> list[Hit]`，所以上层不需要知道底下用的是哪一种。

### 生成层
生成层把命中的片段拼成带编号的资料，再交给 LLM 生成回答。
拼上下文的格式是 `[1] 来源：文件（标题路径）`，编号和资料一一对应。

### 接口层
接口层是 FastAPI 的三个端点：`/health`、`/ingest`、`/query`。
它只做参数校验和序列化，业务逻辑都放在 RagService 里。

## 一次提问的完整数据流

1. 问题先被 embedder 编码成向量。
2. 向量检索和 BM25 各自返回 top_k 个候选。
3. 混合检索用 RRF 把两路名次融合，取前 top_k 个。
4. 命中为空则直接返回兜底话术，不调用模型。
5. 有命中就把片段拼进提示词，调用 LLM，返回答案与引用来源。

## 为什么不做向量数据库

万级片段以内，一次全量矩阵乘法只要毫秒级，比引入一个外部服务划算得多。
数据量再上一个量级，把 VectorStore 换成 pgvector 或 FAISS 才是合理顺序。
