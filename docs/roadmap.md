# 已知不足与下一步

## 评估语料偏小

当前语料切出不到三十个片段，Recall@5 会饱和，阈值的效果也测不出来。
下一步是把语料扩到百量级片段，让指标真正有区分度。

## 向量通道需要真实模型

本地假向量是词袋模型，和 BM25 信息高度重叠，消融里体现不出混合检索的优势。
需要换成真实 embedding 再跑一次评估，才能验证融合到底带来了多少增益。

## 阈值待调参

min_score 现在取 0.15，是从经验来的，没有数据支撑。
评估语料扩容后，可以扫一遍阈值，画出「召回」与「答错」的权衡曲线。

## 关键词索引待持久化

BM25 每次检索都全量重建索引，语料上万片段后这一步会成为瓶颈。
届时需要落一个倒排索引，或者换成带 BM25 的检索引擎。

## 存储可替换

VectorStore 是唯一碰向量的地方，换成 pgvector 或 FAISS 只需要实现同名方法。
真正的触发条件是数据量：毫秒级变成秒级的时候，就该换。

## 可以加重排

召回之后可以再上一个交叉编码器做精排，把最相关的片段顶到第一位。
前提是召回已经做扎实，否则重排只是在垃圾里挑相对好的。

## 多轮对话

需要会话状态、指代消解和查询改写，属于独立一层。
有了它才能回答「那它呢」这类依赖上文的问题。

## 流式输出

把生成结果按 token 推给前端，改善长回答的等待体验。
接口要从返回字符串改成事件流，涉及面比较广。

## 文档权限

不同用户可见的文档范围不同，需要在检索层做过滤。
常见做法是给片段带上租户或标签，检索时先过滤再算相似度。

## 增量导入

当前导入以文档为单位整体替换，文档很大时会重复计算向量。
可以按内容哈希判断片段是否变化，只重算变动的部分。
