# 设计取舍

## 为什么用 SQLite 加 numpy

万级片段以内，一次全量矩阵乘法是毫秒级，比引入向量数据库省掉一个外部依赖。
先讲清楚「检索本质是算相似度」，需要时再换 pgvector 或 FAISS 才是合理顺序。

## 为什么上混合检索

向量擅长意思相近，但对型号、代码标识符这类低频精确词容易漏召。
BM25 恰好相反，两者互补，所以做成两个通道再加融合。

## 为什么用 RRF 而不用加权求和

余弦在 -1 到 1 之间，BM25 无上界，分数量纲不同不能直接相加。
RRF 只取名次，天然回避量纲问题，也不用为权重调参。

## 为什么不做重排

重排需要再引入一个模型，属于召回之后的精排阶段。
当前语料规模下 top-5 已经能覆盖大部分答案，先把召回做扎实更划算。

## 为什么关键词索引每次重建

BM25 每次检索前用 iter_chunks 重建索引，几十毫秒。
换来的是不用维护增量索引的一致性；语料再大就该换持久化倒排索引。

## 为什么切分要带标题路径

切片之后单块会失去上下文，一句话离开所属标题就可能看不懂。
把标题路径拼进片段文本，既让向量带上语境，也让返回结果自带出处。

## 为什么保留重叠

关键句子正好落在切分边界上时，两边都拿不到完整信息。
相邻片段保留一段重叠，用少量冗余换边界处的召回。

## 为什么不做多轮对话

多轮要维护会话状态、做查询改写，是独立的一层能力。
当前接口是单轮问答，先让检索和生成的链路可测、可评估。

## 为什么不做文档权限

权限属于工程层的多租户问题，需要接入真实用户体系。
当前版本假设知识库是单一可见范围，不假装做了隔离。

## 为什么默认装配假实现

默认跑 FakeEmbedder 和 FakeLLM，仓库 clone 下来就能跑通全链路。
换成真实服务只需要替换两个构造参数，这也是接口抽象的收益。
