# RAG 知识库问答服务

把文档喂进来，就能带引用地回答关于这些文档的问题。

链路：文档 → 切分 → 向量化 → 入库；提问 → 检索 → 拼上下文 → 模型回答 → 返回引用来源。

## 快速开始

pip3 install -r requirements-dev.txt
python3 -m pytest -q
python3 -m eval.run_eval --verbose
python3 -m uvicorn app.main:app --reload

## 接口

- GET /health ：健康检查，返回已入库片段数
- POST /ingest ：入库一篇文档
- POST /query ：提问，返回答案与引用来源

## 设计取舍

- 切分带标题路径与重叠：切碎后单片会失去上下文，重叠避免关键句被切在边界上。
- 混合检索而不是纯向量：向量擅长语义相近，但对型号、代码标识符这类低频精确词容易漏召，BM25 恰好相反。
- 融合只用名次（RRF）不用分数：余弦在 [-1, 1]，BM25 无上界，量纲不同不能直接加权。
- 无命中就不调用模型：低于阈值直接返回没有找到相关内容，既防幻觉也省成本。
- SQLite + numpy 而不是向量数据库：万级片段以内，一次矩阵乘法比引入外部服务划算。

## 评估（检索质量）

`eval/` 是一套最小可用的检索评估：42 条标注问答对（精确词与语义改写两类）。
每条标注记录答案所在的标题路径和一个锚点句，跑之前先校验锚点是否真的落在该标题下——
标注写错了就先修标注，而不是去调检索参数。

```bash
python3 -m eval.run_eval --verbose          # 默认假向量，离线可复现
python3 -m eval.run_eval --sweep            # 扫描切分参数
python3 -m eval.run_eval --embedder openai  # 换真实向量（需要 OPENAI_API_KEY）
```

当前结果（14 篇文档 / 102 个片段 / 42 条标注 / k=5，见 `eval/report.md`）：

| 检索通道 | Recall@5 | Hit@1 | MRR |
| --- | --- | --- | --- |
| hybrid RRF（生产默认，候选池 3×） | 0.929 | 0.643 | 0.775 |
| hybrid（候选池 5×） | 0.952 | 0.643 | 0.781 |
| hybrid（候选池 1×，旧实现） | 0.929 | 0.643 | 0.770 |
| vector 单通道 | 0.905 | 0.548 | 0.710 |
| BM25 单通道 | 0.952 | 0.738 | 0.826 |

四个诚实的读法：

- 混合检索的召回追平了最强的单通道（0.952），但 Hit@1 与 MRR 仍低于 BM25：本地假向量是词法的，和 BM25 信息高度重叠，融合时只能稀释精度，带不来新召回。要验证「混合检索更好」，必须换真实 embedding 重跑。
- 候选池扩展是评估逼出来的改动：旧实现让每个通道只取 top_k 条，某通道排第 k 位的命中会在融合前被丢掉。改成先取 top_k × 3 条再融合（`HybridRetriever.candidate_pool`），并补了单元测试证明它能把被截断的命中捞回来。在本语料上它只影响 1 题，差异不显著——这一点也如实写在这里。
- 阈值 0 与 0.15 结果完全一致，说明没有一条命中落在 [0, 0.15) 区间；调阈值需要更长尾的负样本语料才测得出来。
- 42 条标注里精确词 19 条、语义改写 23 条，样本量仍然偏小：单个通道之间 1 题的差距不足以当作结论。

所以这份评估当前的价值不在那个小数点上，而在于流程可复现、标注可自校验、通道对比随时能重跑，
以及它真的逼出了一处实现缺陷。

## 已知不足

- 测试用的 FakeEmbedder 是词袋哈希，只能验证流程与排序，验证不了真实语义召回。
- 向量存在内存 SQLite，进程重启即丢失。
- 关键词检索每次全量重建索引，语料再大需要持久化倒排索引。
- 评估仍用本地假向量：混合检索相对单通道的增益无法验证，需要 `--embedder openai` 重跑消融。
- 阈值（min_score）没有数据支撑，当前没有任何一条命中落在 0.15 以下，调参需要构造更难的长尾负样本。
- 暂无多轮对话、文档权限隔离、流式输出。
- 默认装配的是假模型，换成 OpenAIChat 与 OpenAIEmbedder 即可接真实服务。

## 测试策略

- 不联网不花钱：Embedder、LLM、服务全部通过构造器注入替换成假实现。
- 接口层用 create_app(service) 注入，业务代码一行不改，测的是真实代码路径。
- 覆盖切分边界与参数校验、向量维度校验、RRF 融合去重、无命中兜底、HTTP 参数校验。
- 现有 63 个用例；CI 在 Python 3.10 / 3.12 / 3.14 上跑 pytest，并额外跑一遍检索评估——标注写错会让 CI 直接变红。
